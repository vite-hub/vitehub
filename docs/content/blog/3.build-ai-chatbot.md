Most AI chat examples start with a model call. That is fine for a demo, and it
is also the right place to start here. The first version should prove the Agent
can run before it knows anything from your files.

Then you add context deliberately. ViteHub uses [Workspace Sources](/docs/server-primitives/workspace)
for that: a Source can be a local file, a glob, a fetched document, a GitHub
repo, or any other read-only origin that exposes addressable items through a
Workspace.

That gives you a better shape than a model call hidden in a route. The [Agent Definition](/docs/agents/agent-definitions)
grows from a tiny chat actor into a reviewable server-side declaration that
names the model, instructions, Capabilities, and Workspace Sources.

This post builds a support Agent in layers: first chat, then `AGENTS.md`, then a
GitHub Source, then DevTools inspection, and finally an Agent Eval.

::code-tree-intersection{default}
```ts [server/agents/support/config.ts]
import { gateway } from '@ai-sdk/gateway'
import { defineAgent } from '@vite-hub/agent'
import { chat } from '@vite-hub/agent/capabilities'

export default defineAgent({
  model: gateway('openai/gpt-5.1-mini'),
  instructions: 'Answer support questions in a short, concrete style.',
  capabilities: [
    chat(),
  ],
})
```
::

The first code sample is intentionally small:

- `model` chooses the model execution path.
- `instructions` gives the Agent durable behavior.
- `chat()` adds a chat-oriented Capability.

No Workspace, no `AGENTS.md`, no files yet. The next sections add those only
after the Agent can answer a message. Read [Instructions](/docs/agents/instructions)
and [Capabilities](/docs/agents/capabilities) for the full model.

::collapsible{name="setup commands" open-text="Show" close-text="Hide" class="setup-collapsible"}
You need Node 20.19+ or Node 22.12+, `pnpm`, and a model provider key for the AI
SDK Gateway model you choose.

Create a local env file and set the Gateway key.

```dotenv [.env]
AI_GATEWAY_API_KEY=
```

Install the packages used in this example.

```bash [Terminal]
pnpm add @vite-hub/agent @vite-hub/workspace
pnpm add @vite-hub/devtools @ai-sdk/gateway ai
pnpm add -D @vitejs/devtools
```

Register the Vite Integrations in `vite.config.ts`.

```ts [vite.config.ts]
import { hubAgent } from '@vite-hub/agent/vite'
import { hubDevtools } from '@vite-hub/devtools'
import { hubWorkspace } from '@vite-hub/workspace/vite'
import { DevTools } from '@vitejs/devtools'
import { defineConfig } from 'vite'

export default defineConfig(async () => ({
  plugins: [
    ...(await DevTools()),
    hubDevtools(),
    hubWorkspace(),
    hubAgent(),
  ],
}))
```

The Vite Integrations are where ViteHub wires definitions to the host. The Agent
Definition stays focused on the Agent itself.
::

## First Chat Agent

Start with the smallest Agent that can receive a chat message.

::code-tree-intersection
```ts [server/agents/support/config.ts]
import { gateway } from '@ai-sdk/gateway'
import { defineAgent } from '@vite-hub/agent'
import { chat } from '@vite-hub/agent/capabilities'

export default defineAgent({
  model: gateway('openai/gpt-5.1-mini'),
  instructions: 'Answer support questions in a short, concrete style.',
  capabilities: [
    chat(),
  ],
})
```
::

This is a real Agent Definition, but it only has model behavior and chat. It can
respond, but it cannot inspect project context yet.

`chat()` is a Capability. Capabilities are the opt-in abilities an Agent can
use; they contribute tools, instructions, triggers, policy, and runtime metadata.
Read [Official capabilities](/docs/agents/capabilities/official-capabilities)
for the catalog.

## Add a Workspace

A Workspace is more than the host filesystem. It is a persistent Workspace File
Tree populated by Sources. Server code and Agents can inspect or mutate that tree
only through the access you configure.

Add an `AGENTS.md` file beside the Agent, then declare it as a Source.

::code-tree-intersection
```md [server/agents/support/workspace/AGENTS.md]
# Support Agent

Answer support questions from this file.
If this file does not contain the answer, say so.

## Support policy

Refunds are available within 30 days when the order has not shipped.
```

```ts [server/agents/support/config.ts]
import { gateway } from '@ai-sdk/gateway'
import { defineAgent } from '@vite-hub/agent'
import { chat, workspaceShell } from '@vite-hub/agent/capabilities'
import { file } from '@vite-hub/workspace'

export default defineAgent({
  model: gateway('openai/gpt-5.1-mini'),
  workspace: {
    sources: {
      instructions: file('AGENTS.md'),
    },
  },
  instructions: async ({ fs }) => await fs.readFile('AGENTS.md'),
  capabilities: [
    chat(),
    workspaceShell({ mode: 'read' }),
  ],
})
```
::

The `workspace/` directory is the Workspace Source Root for this colocated
definition. `file('AGENTS.md')` exposes the file through the Workspace
File Tree, and `workspaceShell({ mode: 'read' })` lets the Agent inspect that
tree during an Agent Invocation.

This split matters. The Workspace declares what exists. The Workspace Shell
Capability decides what the model can do with it. Read [Workspace context](/docs/agents/workspace-context)
for the Agent-specific model.

## Add a GitHub Source

Sources do not have to be local files. A Source is any named origin that exposes
read-only addressable files or items through the Workspace. GitHub is a good
example because product answers often depend on docs or code that live outside
the current app.

Add the ViteHub docs repo as a GitHub Source.

::code-tree-intersection
```md [server/agents/support/workspace/AGENTS.md]
# Support Agent

Answer support questions from this file.
If this file does not contain the answer, say so.
For ViteHub product docs, inspect `vitehub-docs`.

## Support policy

Refunds are available within 30 days when the order has not shipped.
```

```ts [server/agents/support/config.ts]
import { gateway } from '@ai-sdk/gateway'
import { defineAgent } from '@vite-hub/agent'
import { chat, workspaceShell } from '@vite-hub/agent/capabilities'
import { file, github } from '@vite-hub/workspace'

export default defineAgent({
  model: gateway('openai/gpt-5.1-mini'),
  workspace: {
    sources: {
      instructions: file('AGENTS.md'),
      vitehubDocs: github({
        repo: 'vite-hub/vitehub',
        root: 'docs/content/docs',
        include: ['**/*.md'],
        mount: 'vitehub-docs',
        materialize: 'lazy',
        instructions: 'Use this GitHub Source for public ViteHub documentation.',
      }),
    },
  },
  instructions: async ({ fs }) => await fs.readFile('AGENTS.md'),
  capabilities: [
    chat(),
    workspaceShell({ mode: 'read' }),
  ],
})
```
::

The Agent still sees one Workspace File Tree. The local file appears at
`AGENTS.md`, and the GitHub Source appears under `vitehub-docs`. ViteHub does
not load nearby files or remote repositories by surprise; each Source stays
visible in the Agent Definition.

`materialize: 'lazy'` keeps the GitHub Source lazy until the Workspace needs to
read it. In other words, ViteHub can expose the remote repo as addressable
context without eagerly copying every file into the Workspace Store. For private
repositories, provide `GITHUB_TOKEN` in the runtime environment.

## Try it in DevTools

Run the app:

```bash [Terminal]
pnpm dev
```

Open Vite DevTools, choose **ViteHub**, then open **Chat**. Select the
`support` Agent and ask:

```txt
What is our refund policy, and where should I read about Workspace Sources?
```

The Agent should answer with the 30-day refund window and point at the Workspace
docs. In the DevTools timeline, inspect the Agent Invocation and any Workspace
tool calls that happened before the answer.

That is the useful part of the local loop. If the Agent cannot answer the refund
question, first check that `AGENTS.md` is declared as a Source and loaded by
`instructions`. If it cannot answer the docs question, check that the GitHub
Source is declared and reachable. If the Sources are present and the answer is
still wrong, tune the instructions. Read [Agent DevTools](/docs/agents/devtools)
for the inspection workflow.

## Evals

Once the answer is right, save the expectation in
`server/agents/support/eval.ts`.

::code-tree-intersection
```ts [server/agents/support/eval.ts]
import { defineEval, textContains } from '@vite-hub/agent/eval'
import support from './config'

export default defineEval({
  agent: support,
  scenarios: [
    {
      name: 'answers refund policy',
      input: {
        prompt: 'What is our refund policy?',
      },
      scorers: [
        textContains('30 days'),
      ],
    },
  ],
})
```
::

The eval points at the same Agent Definition and runs the same Agent Invocation
path. Use Agent Evals for behavior you want to keep, not for every prompt you
try manually. Read [Agent Evals](/docs/agents/evals) for the full shape.

## Grow the Agent by adding Capabilities

The support Agent only needs `chat()` and `workspaceShell()`. A larger Agent can
attach more Capabilities in the same list:

- `skills()` loads project instructions from `SKILL.md`.
- `webSearch()` searches and reads the web.
- `mcp()` connects MCP server tools.
- `sandbox()` runs approved commands in isolation.
- `transcribe()` converts audio to text.
- `kv()`, `blob()`, and `db()` expose scoped storage.
- `llmGate()` rejects unsafe or unwanted requests.
- `llmRoute()` chooses the right path for a request.
- `usageTelemetry()` records model usage and cost.

The API should stay ordinary on purpose. Read the Agent Definition, see the
model, see the Capabilities, and see the Workspace Sources the Agent can use.

## Deploy the same Agent

The Agent Definition is not a Vercel route, a Cloudflare Worker, or a Docker
entrypoint. It is the portable definition ViteHub discovers during the Vite
build.

Choose the host at the integration layer:

- **Vercel** runs the Agent through Vercel Provider Output. Keep model keys,
  Blob credentials, and other Runtime Config in Vercel environment variables.
- **Cloudflare** runs the Agent through Cloudflare Provider Output. Bind Worker
  resources such as R2, KV, Queues, Durable Objects, or Agent state where a
  Capability needs them.
- **Docker** runs the same hosted Node server build in a container. Provide the
  same Runtime Config through environment variables or mounted secrets.

The code in `server/agents/support/config.ts` does not change for each host.
The host changes deployment output, bindings, storage, and environment
variables.
