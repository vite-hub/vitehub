JavaScript makes frontend work feel fast, typed, and composed. Then you add
storage, queues, scheduled jobs, workflows, or AI agents, and the server side
often pulls you back into provider wiring.

ViteHub starts from that frustration.

The goal is to make server features feel like the best parts of the Nuxt
ecosystem: good defaults, clear files, typed APIs, and enough escape hatches to
use the platform underneath. You choose the provider in configuration. Your
application code stays focused on the product.

ViteHub starts with Vite and Nitro v3 because the
[Vite Environment API](https://vite.dev/guide/api-environment) opens a new way
to build server features. The long-term goal is to make the same
provider-agnostic primitives available to every Vite-based framework, from Nuxt
to TanStack and SvelteKit.

## The problem

Over the last few years, the frontend ecosystem made Vite the shared foundation
for client-side development. Vue, React, Svelte, Nuxt, TanStack, and other
frameworks can use the same bundler, plugin model, and fast feedback loop
without becoming the same framework. The server side needs that same kind of
shared foundation.

Server work still feels more fragmented. Uploads, key-value state, databases,
queues, workflows, scheduled jobs, sandboxes, and AI agents often begin with a
provider SDK. That works, but it also spreads infrastructure details across
routes, handlers, and tests.

The cost shows up later. Local development becomes harder to trust, and provider
choices start leaking into product code. You should be able to keep the same
application code and switch providers at the framework boundary. Small features
should not turn into rewrites across routes, handlers, and tests.

## The idea

ViteHub moves provider wiring to the framework boundary.

The shape is easiest to see in code. Each primitive has a definition surface
when it needs one, and a small Runtime Helper for the application code that uses
it.

::tabs{class="gap-0"}

:::tabs-item{label="Database"}

```ts [server/db/schema.ts]
import { defineDatabase } from '@vite-hub/database'
import { integer, sqliteTable, text } from 'drizzle-orm/sqlite-core'

export default defineDatabase({
  schema: {
    notes: sqliteTable('notes', {
      id: integer('id').primaryKey(),
      title: text('title').notNull(),
      body: text('body').notNull(),
    }),
  },
})
```

```ts [server/api/notes.get.ts]
import { db, schema } from '@vite-hub/database/drizzle'

export default defineEventHandler(() => {
  return db.select().from(schema.notes)
})
```

:::tabs-item{label="KV"}

```ts [server/api/settings.put.ts]
import { kv } from '@vite-hub/kv'

export default defineEventHandler(async (event) => {
  await kv.set('settings', await readBody(event))
  return { ok: true }
})
```

```ts [server/api/settings.get.ts]
import { kv } from '@vite-hub/kv'

export default defineEventHandler(async () => {
  return {
    settings: await kv.get('settings'),
  }
})
```

:::tabs-item{label="Workflow"}

```ts [server/workflows/onboard-user.ts]
import { defineWorkflow } from '@vite-hub/workflow'

export default defineWorkflow<{ email: string }>(async ({ payload, step }) => {
  const user = await step.run('create-user', () => createUser(payload.email))
  await step.run('send-email', () => sendWelcomeEmail(user.email))

  return { userId: user.id }
})
```

```ts [server/api/onboard.post.ts]
import { runWorkflow } from '@vite-hub/workflow'

export default defineEventHandler(async (event) => {
  const body = await readBody<{ email: string }>(event)
  return runWorkflow('onboard-user', body)
})
```

Provider-agnostic does not mean lowest common denominator. Cloudflare, Vercel,
and local development each have their own SDKs, runtime behavior, and platform
features. ViteHub builds on top of those provider APIs instead of replacing
them. The goal is to create a common API where that makes product code clearer,
while still leaving a path to provider-specific features when the platform has
something worth reaching for.

That is the payoff: portable product code without pretending every platform is
the same. You can switch providers without rewriting the feature, but you can
still reach for the provider features that matter.

## Better Agents

The agent API came from a different pressure. While building ViteHub's server
primitives, I also had to build agents and bots for real projects. I expected to
need a separate agent framework, but the useful pieces were already there:
storage, queues, workflows, sandboxes, Workspaces, and a shell.

The next realization was Workspace Shell. Vercel has written about
[filesystems and bash as an agent abstraction](https://vercel.com/blog/testing-if-bash-is-all-you-need),
and that matched what I was seeing: agents need files, commands, and fast ways
to build context. In ViteHub, Workspace is the knowledge boundary. Shell access
makes that boundary useful without hiding it. That deserves its own post.

That led to Agent Definitions. One file can define the model provider through
the AI SDK, the Workspace it can inspect, and the Capabilities it can use. The
model can change, the host can change, and the agent can still receive the same
kind of explicit access to chat, memory, voice transcription, storage, shell
access, MCP, skills, and whatever comes next.

That idea did not come from nowhere.

## Acknowledgements

ViteHub follows ideas I already trust.

[Better Auth](https://better-auth.com/) showed me that a composable plugin
system can stay readable as it grows. ViteHub applies that shape to agents: one
clear file, explicit capabilities, and room for the app to grow without losing
control.

[Nuxt Hub](https://hub.nuxt.com/) showed me how full-stack features can feel
native to a framework without hiding storage, deployment, and runtime details.
Seeing [Void](https://void.cloud/) follow a similar Cloudflare-first path for
more frameworks made the tradeoff clear again. I understand why a team would
choose that focus, but I think the better abstraction is provider-agnostic.

[UnJS](https://unjs.io/) has already shown that provider-agnostic libraries can
be small, tested, and pleasant to use. ViteHub builds on that foundation and
borrows from its API discipline, code structure, and architecture.

Laravel is another reference point, less for any single feature than for the
developer ecosystem around it. People love building with it because the pieces
feel coherent. JavaScript should be able to earn that same kind of trust on the
server without locking the app into one host.

## The developer experience

ViteHub is designed to remove the boring work without removing control.

You get sensible defaults for local development. You keep provider choice in
configuration. You can review a feature by opening a few files instead of
chasing setup across the codebase.

The important part is not the architecture diagram. The important part is what
it removes from your day: duplicated provider setup, fragile local mocks,
runtime configuration spread across handlers, and migration work that touches
business logic.

Good API design matters here. The primitives need to feel small, but not
limited. They need to hide the repetitive wiring, but not the platform power.

## Where it is going

ViteHub is still early, and that is why I want to share it now. The foundation
is useful enough to build with, but there is a lot of work ahead:

- more provider coverage
- stronger tests across Vite, Nitro, Cloudflare, and Vercel
- better examples for real product flows
