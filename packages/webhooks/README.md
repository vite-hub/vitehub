# @vite-hub/webhooks

`@vite-hub/webhooks` sends your app's events to a URL outside the app: a new comment, a form submit, a blob upload, a Content publish, or an Auth event. Each delivery is signed, stored, retried, and can wait for a debounce, on every host.

## Define a webhook

```ts [server/webhooks/t3.ts]
import { defineWebhook } from "@vite-hub/webhooks"

export default defineWebhook({
  url: "T3_WEBHOOK_URL",
  secret: "T3_WEBHOOK_SECRET",
  signature: "github",
  debounce: "30 minutes",
})
```

| Option | Does |
| --- | --- |
| `url` | The name of the server variable that holds the receiver URL. It is a name, not the URL, because a URL often holds a token. |
| `secret` | The name of the server variable that holds the signing secret. |
| `signature` | `"github"` (default) sends `x-hub-signature-256: sha256=<hex>`. `"stripe"` sends `stripe-signature: t=<time>,v1=<hex>`. `verifyWebhook()` from `@vite-hub/env` checks both. |
| `debounce` | Optional. Waits this long after the last send, then delivers once. A duration such as `"30 minutes"` or `"10s"`, at most 24 hours, the longest delay of Cloudflare Queues. |
| `events` | Optional. Events that ViteHub sends by itself: `"invocation.failed"`, `"workflow.failed"`, and `"schedule.failed"`. See [Failure alerts](#failure-alerts). |

The file name is the webhook name: lowercase letters, digits, and dashes. The app needs `queue` and `database` in `vitehub()`, with a SQLite Default Database such as libSQL or D1. Without them, the build fails with `WEBHOOKS_QUEUE_OFF` or `WEBHOOKS_DATABASE_OFF`. Run `vitehub database generate` and `vitehub database migrate` to add the table.

## Send events

This excerpt uses the webhook names generated by the app build.

```ts [server/comments.ts] fragment
import { defineComments } from "vite-hub/comments"
import { sendWebhook } from "vite-hub/webhooks"

export const comments = defineComments({
  onComment: async ({ thread, message }) => {
    const [error] = await sendWebhook("t3", { thread: thread.id, message: message.id }, { event: "comments.comment" })
    if (error) console.error(error)
  },
})
```

`sendWebhook(name, body, { event, key? })` returns `[error, { id, status: "pending" }]`. The name is typed from the files of `server/webhooks/`. A missing variable, a body that is not JSON, or a Database or Queue failure comes back as the error. An unknown name throws.

The receiver gets a `POST` with the JSON body and these headers:

| Header | Value |
| --- | --- |
| `content-type` | `application/json` |
| `x-hub-signature-256` or `stripe-signature` | The signature of the body |
| `x-vitehub-event` | The `event` of the last send |
| `x-vitehub-delivery` | The delivery id. It stays the same for every retry, so the receiver can drop a duplicate. |
| `x-vitehub-events` | How many sends the debounce collapsed into this delivery |

## Failure alerts

A webhook that lists `events` gets each failed run without a `sendWebhook()` call:

```ts [server/webhooks/alerts.ts]
import { defineWebhook } from "@vite-hub/webhooks"

export default defineWebhook({
  url: "ALERTS_WEBHOOK_URL",
  secret: "ALERTS_WEBHOOK_SECRET",
  events: ["invocation.failed", "workflow.failed", "schedule.failed"],
  debounce: "10 minutes",
})
```

Agent, Workflow, and Schedule send the event when a run fails with no retry left. The body has the `event`, the Agent, Workflow, or Schedule name, the run or Invocation id, `error: { message, code? }`, `failedAt`, and `text`, one line that a Slack incoming webhook shows as the message. With `debounce`, failures of the same Agent, Workflow, or Schedule collapse into one delivery. The run must execute in a process that loads the app's Webhooks. Standalone cron entries, including Vercel and Netlify cron functions, and Vercel Workflow DevKit (`native`) runs do not send these events.

## How a delivery works

1. `sendWebhook()` stores the delivery in the `vitehub_webhook_deliveries` table of the Default Database, then sends a wake job to the internal `vitehub-webhooks` Queue with the debounce as its delay.
2. With a debounce, a send with the same `key` (default: the webhook name) replaces the body of the pending delivery, raises its revision, and sends a new wake. Only the wake of the latest revision delivers, so the receiver gets the last body once.
3. The wake posts the delivery with a 10 second timeout. A 2xx answer marks it `sent`. Any other answer, a timeout, or a network error throws, so the Queue tries again with the same delivery id. After 4 attempts it is `dead`.
4. A missing variable at delivery time marks it `dead` at once, because a retry cannot help.

Errors and stored fields never hold the URL, its query, or the secret. A delivery is one of `pending`, `sending`, `sent`, `dead`, or `cancelled`.

## Member endpoints

A member endpoint is a receiver that belongs to one member of the app, such as their T3 Code thread. A feature that sends to members turns them on, such as Send in Comments, or a Vite plugin with `vitehub.webhooks: { memberEndpoints: true, reason }`. They need `database`, not `queue`.

```ts [server/utils/send-comments.ts]
import { createMemberEndpoint, sendToMemberEndpoint } from "vite-hub/webhooks"

export async function connectAndSend(userId: string, url: string, secret: string) {
  const [connectError] = await createMemberEndpoint({ owner: userId, name: "Launch plan thread", agent: "t3", kind: "url", url, secret })
  if (connectError) return connectError.code
  const [error, sent] = await sendToMemberEndpoint(userId, { threads: ["thr_1"] }, { event: "comments.send", key: "thr_1:msg_8" })
  return error ? error.code : sent.status
}
```

| Function | Does |
| --- | --- |
| `createMemberEndpoint({ owner, ownerName?, ownerEmail?, name, kind, url?, secret?, agent?, address?, hosts? })` | Stores a member's receiver. `kind` is `"url"` or `"inbox"`. The URL must pass `checkWebhookUrl()` with `hosts`, which defaults to `relay.t3.codes`. `address` says where the agent can be reached, such as its T3 thread URL: a member has one endpoint per address, and a new one replaces the one with the same address. |
| `sendToMemberEndpoint(owner, body, { event, key, address?, endpointId? })` | Posts to the member's endpoint with `address`, else to their newest. Pass `endpointId` to send only to that endpoint with no fallback. Posts in the request with a 10 second timeout and the usual signature. The same `key` posts once per endpoint. Returns `[error, { id, status }]`, where `status` is `"sent"`, `"inbox"`, `"pending"` (the Queue retries), or `"failed"`. |
| `listMemberDeliveries(owner, { address?, endpointId?, limit?, before? })` | The selected endpoint and its deliveries, newest first, or `null`. Inbox agents should pass the `endpointId` from pairing so their reads never switch to another endpoint. An empty `address` prefers the unaddressed endpoint. |
| `startMemberPairing(owner)`, `pairMemberEndpoint(input, { hosts? })`, `allowMemberPairing(owner, code, { name, ownerName?, ownerEmail?, hosts? })` | Pair a member's agent with a one-use code that works for 10 minutes. Give the agent the `code` and `secret` that start returns. A route passes its post, `{ code, url, thread? }` or `{ code, inbox }`, to `pairMemberEndpoint`, and the member's Allow creates the endpoint, with the agent's T3 thread link as its address. `getMemberPairing`, `cancelMemberPairing`, and `refuseMemberPairing` poll, close, and use up a code. Comments Send pairs this way. |
| `getMemberEndpoint(owner, { endpointId?, address? })`, `listMemberEndpoints({ limit?, after? })`, `removeMemberEndpoint(owner, id)`, `removeMemberEndpoints(owner)`, `disableMemberEndpoint(id, { by? })`, `enableMemberEndpoint(id)` | Read, list a page with the newest delivery to each endpoint, remove, disable, or enable an endpoint. None returns the receiver URL or the secret. |
| `checkWebhookUrl(url, { hosts? })` | Refuses a URL that is not `https`, holds credentials, uses a host outside `hosts`, or names or resolves to a loopback, private, link-local, or metadata address. Cloudflare Workers cannot resolve names, so there `hosts` alone decides. |

The URL and secret are sealed with AES-GCM and `VITEHUB_WEBHOOKS_KEY` (32 bytes in base64, from `openssl rand -base64 32`). `vite dev` generates one in `.vitehub/data/webhooks-key`. Without it in production, the functions return `WEBHOOKS_KEY_UNSET`. Each send is a delivery with `webhook: "@<endpoint id>"`. Only its owner can redeliver it or send it now: an app user whose id is `owner`, or a ViteHub Console account whose verified email matches `ownerEmail` and still resolves to `owner` in the app's Auth. Anyone else gets `WEBHOOKS_DELIVERY_NOT_OWNER` (403).

## Inspect and operate

`@vite-hub/webhooks/runtime` reads and changes deliveries in server code. Each function returns `[error, data]`.

| Function | Does |
| --- | --- |
| `listWebhooks()` | Every webhook, with the names of its variables, whether they are set, and the URL host |
| `listWebhookDeliveries({ webhook?, state?, limit?, before? })` | Deliveries, newest first |
| `listPendingWebhookDeliveries({ webhook?, limit? })` | Pending deliveries, the soonest due first |
| `getWebhookDelivery(id)` | One delivery |
| `flushWebhookDelivery(id, { caller? })` | Delivers a pending delivery now |
| `cancelWebhookDelivery(id)` | Cancels a pending delivery |
| `redeliverWebhookDelivery(id, { caller? })` | Sends a sent, dead, or cancelled delivery again as a new delivery. A member delivery needs its owner as `caller`, such as `{ id: user.id }`. |
| `testWebhook(name, { body? })` | Sends a test delivery now, without the debounce, with the event `webhooks.test` |

The same actions run from the terminal, the Console, and MCP as the `webhooks.*` operations on the app's operation RPC. `vitehub webhooks` reaches `vite dev`, or a deployed app with `--url`, and prints JSON:

```bash
vitehub webhooks list
vitehub webhooks deliveries --webhook t3 --state dead --limit 20
vitehub webhooks pending
vitehub webhooks get whd_...
vitehub webhooks test t3 --body '{"thread":"thr_1"}'
vitehub webhooks flush whd_...
vitehub webhooks cancel whd_...
vitehub webhooks redeliver whd_...
vitehub webhooks endpoints
vitehub webhooks deliveries --owner user_ana
vitehub webhooks disable-endpoint whe_...
vitehub webhooks enable-endpoint whe_...
```

`list`, `deliveries`, `pending`, `get`, and `endpoints` only read, so MCP marks them read-only. The output shows the host of a URL, never its path, query, or the secret.

The Webhooks section of the Console shows each webhook with its host, signature, debounce, and the names of its URL and secret variables, then the pending timers with a countdown and the delivery log. Its buttons run Send test, Send now, Cancel, and Redeliver through the same operations. Set the variables in the Env section. With member endpoints on, it lists them first, read-only, with Disable and Enable, and the log filters by owner and endpoint.
