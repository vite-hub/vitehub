`@vite-hub/internal` is a private workspace package for shared implementation code. Application code should not import it.

## Install

Do not install this package directly. Other ViteHub packages depend on it inside the monorepo.

## Minimal API

```ts
// packages/*/src/internal-use.ts
import { createRuntimeRegistryContents } from "@vite-hub/internal/definition-catalog"
import { createNoExternalAddition } from "@vite-hub/internal/build/vite"
import { normalizeHosting } from "@vite-hub/internal/hosting"
import { summarizeDefinitions } from "@vite-hub/internal/inspect"
import { readViteHubConsoleSection } from "@vite-hub/internal/console"
import { discoverViteHubDevServer } from "@vite-hub/internal/cli"
import { registerViteHubDevEndpoint } from "@vite-hub/internal/dev-endpoint"
```

Source readers use `createSourceScanner(file)` from `@vite-hub/internal/source-scanner` to bind the file grammar. Its matching, splitting, object, and comment readers keep that grammar for source fragments. The standalone readers use JavaScript and TypeScript grammar without JSX. Filenames that end in `.jsx` or `.tsx` enable JSX, with TypeScript generic heads recognized only for `.tsx`.

## Used by

Packages use it for definition discovery, generated runtime registries, Provider Output, hosted runtime helpers, and hosting normalization.

The shared deployment output writer minifies identifiers, syntax, and whitespace in final Cloudflare, Vercel, and Netlify bundles. Each bundle can disable a pass with `bundleOptions.minifyIdentifiers: false`, `bundleOptions.minifySyntax: false`, or `bundleOptions.minifyWhitespace: false`. Netlify functions with an appended static config always minify identifiers to avoid config binding collisions. Syntax and identifier minification preserve function and class names, even when only one pass is enabled. Direct `bundleEsmEntry` calls leave all minification off by default, so intermediate generated sources are unchanged.

Provision Steps list Cloudflare resources with `listCloudflarePages(request, path, { parse, perPage })` from `@vite-hub/internal/provision`. It sends `page` (and `per_page` when `perPage` is set) and reads pages until `result_info.total_pages` or `result_info.total_count` says the list is complete. Without that metadata, it stops at a page shorter than `perPage`, or after the first page when `perPage` is not set. An empty page always stops the list. A response for a different page than the one requested throws `INTERNAL_R0010`. R2 bucket lists page with a cursor and do not use it.

`readProvisionState` and `readProvisionStateSync` from `@vite-hub/internal/provision-state` return empty state when `.vitehub/provision.json` is missing. Invalid JSON and other read failures throw `INTERNAL_R0014` with the resolved path and original cause. `writeProvisionState` reads existing state before writing, so a read failure leaves the file unchanged. Valid JSON keeps its filtering policy: non-object roots become empty state, unsupported providers and invalid category shapes are skipped, and only string IDs are retained.

`@vite-hub/internal/provider-failure` turns a failed Cloudflare or Vercel API call into one `ProviderFailureKind`: `not-found`, `conflict`, `throttled`, `unauthorized`, `invalid`, or `unavailable`. `classifyProviderFailure(source, { status, codes })` reads a documented provider code first (Cloudflare `errors[].code` in the table of its product, or Vercel `error.code`) and then the HTTP status. `ProvisionRequestError` keeps the `kind`, the `status`, and the provider `codes` as data. Provider code matches on `kind`, not on the error message or a raw status.

ViteHub writes its own Blob objects, such as Workspace history, Console attachments, and derived caches, under one prefix. `vitehubOwnedPrefix` from `@vite-hub/internal/owned-paths` is `_vitehub/`. Build every ViteHub-owned Blob path from it. `isVitehubOwnedPath(pathname)` returns true for those paths, so a UI that lists a Blob store can hide them and refuse to move or delete them.

Owner packages add a page tool, such as the Comments overlay, with `@vite-hub/internal/runtime/page-tools`. The owner's Nitro plugin calls `registerViteHubPageTool(nitroApp, { id, label, icon, hotkey?, script, allowed })` and then `installViteHubPageTools(nitroApp, { base })`. `script` is a path below the app base, such as `/api/_vitehub/comments/assets/overlay.js`, or a full URL. `base` is the app base from the build, such as the Vite `base`. `viteHubPageToolsWanted(search, cookie)` in `page-tools-shared` is the hint: the `?vitehub` query (`?vitehub=<id>` also opens that tool), the `vitehub-tools=1` cookie, or the `vitehub_session=1` Auth marker without any `vitehub-tools` cookie (a person signed in and the session route has not answered yet). With at least one registered tool, the install adds one script before `</body>` of each HTML page, with the page's CSP nonce:

- A request with the hint gets the loader tag, `<script type="module" src="<base>/_vitehub/page/assets/loader.js?v=18" data-vitehub-page-tools>`, and the page goes out with `cache-control: private, no-store`. When the page has the generated bootstrap, the server replaces it with the loader tag. This also supports a meta CSP that permits same-origin external scripts while blocking inline scripts.
- Any other page, including a prerendered one, gets the bootstrap, `viteHubPageToolsInlineScript(base, nonce?)`: an inline module script, marked `data-vitehub-page-tools`, that runs the same hint rule in the browser and imports the loader only when it is true. It makes no request without the hint and is the same for every visitor, so the page keeps its cache policy. Transformed pages drop upstream `ETag` and `Last-Modified` validators, and GET and HEAD requests explicitly accepting `text/html` omit `If-None-Match` and `If-Modified-Since` so an upstream 304 cannot reuse HTML from before the bootstrap changed. A host that serves prerendered pages as static files, such as Cloudflare Workers static assets, serves the bootstrap with them.

A page that already has a `data-vitehub-page-tools` script gets no second one. A generated bootstrap, including one with a prerender-time nonce, is replaced with the current request's loader or bootstrap and CSP nonce. Without a response nonce, it keeps the existing bootstrap nonce so a meta CSP continues to allow it. It installs once per Nitro app: on Nitro 3 it wraps `fetch`, which the prerenderer also calls, and uses `base`. On Nitro 2 it hooks `render:html` for rendered and prerendered pages and `beforeResponse` for the loader or bootstrap in returned pages, and reads the base of each request (H3 1 removes Nitro's `baseURL` from `url` and keeps it in `originalUrl`). Compressed HTML stays unchanged. Streamed responses and buffered byte responses require an explicit UTF-8 charset; without one, HTML metadata or browser fallback may select a legacy encoding. Paths under `<base>/_vitehub` and `<base>/api/` never get the loader or the bootstrap. Tools belong to one Nitro app. A second register with the same `id` replaces only that app's tool. Registrations and an explicit base supplied after installation take effect on the next request.

`GET <base>/_vitehub/page/session` runs `allowed({ request, event })` of each tool registered for that app and returns `{ tools: [{ id, label, icon, hotkey?, script }] }` with `cache-control: private, no-store`. It takes the base from its own request path, as the Console page does, and adds it to each `script` path. It sets `vitehub-tools=1` when at least one tool is allowed and `vitehub-tools=0` when none is, both for 30 days, so a signed-in person without access asks once per session. The cookie is not `HttpOnly`, because the bootstrap reads it. `@vite-hub/auth` clears it with `viteHubPageToolsResetCookie` when a session starts or ends, so the pill shows right after sign-in. A check that throws counts as not allowed. A request with another `Origin`, or with `Sec-Fetch-Site: cross-site`, gets 403 and runs no check. The hint is never a credential: each tool's API checks access on every call. The owner's Vite plugin serves the route and the loader with `addViteHubPageToolRoutes(kit, { handler, loader, mount })` from `@vite-hub/internal/build/page-tools`, so they work without the Console. The first owner wins; the registry is shared through a `globalThis` slot, so any copy of the handler answers for that app's tools. Nitro 3 binds each Web request to its app; Nitro 2 binds each H3 event in its request hook. An unbound handler returns 503 without running permission checks.

`viteHubPageToolsBase(config)` reads the app base of a Vite configuration: ViteHub's application-base config field or `__VITEHUB_APP_BASE_URL__` constant when set (the Nuxt module sets both from `app.baseURL`), else a root-relative Vite `base`. Absolute and protocol-relative Vite asset CDN URLs leave application routes at the root unless an explicit application base is set. It returns `{ base, mount }`. `mount` is the route prefix for the Nitro configuration: the part of `base` that Nitro's own `baseURL` does not add. The Console mounts its routes with the same rule. `viteHubBasePath()` in `page-tools-shared` turns a base into a path: `/docs/` and `https://cdn.example/docs/` give `/docs`, and `./` gives the root.

A single page app whose `index.html` Vite serves or builds has no server that changes its HTML on a static host. Each owner calls `viteHubPageToolsIndexHtml(html, base)` in its `transformIndexHtml` hook. It adds the bootstrap, which imports `<base>/_vitehub/page/assets/loader.js` when the page has the hint. It returns `undefined` when the HTML already has the marker, so Comments and the Console add one script together.

The loader, `loadViteHubPageTools()` from `@vite-hub/internal/runtime/page-tools-loader`, calls the session route next to its own URL: `<base>/_vitehub/page/assets/loader.js` calls `<base>/_vitehub/page/session`. Without an allowed tool it stops. Otherwise it draws the pill: one `<vitehub-pill>` element with an open shadow root, docked to an edge of the page, at the bottom center by default. The pill starts with the ViteHub mark, then has one named slot per tool, in session order, and one exit button, **Turn off ViteHub tools**. The mark collapses the pill to itself and expands it again. Collapsed, the pill is a small ViteHub hexagon 2px from the edge, so it covers almost nothing of the page. Collapsing only hides the segments and the exit button: the tools keep running, with their windows, pins, and modes. Dragging the mark docks the pill to the closest edge (top, right, bottom, or left) at the place under the pointer, like the floating frame of Nuxt and Vite DevTools. On the left and right edges the buttons stack. Windows open from the docked edge. The browser remembers both choices in `localStorage` (`vitehub-tools-collapsed`, and `vitehub-tools-dock` with `{ edge, at }`, where `at` goes from 0 at the left or top end to 100), so the next pages start the same. A page with its own bar where the pill docks sets `data-vitehub-pill="mark"` (`viteHubPillAttribute`) on `<html>`: while it is set, the pill and the off mark fold to the mark, at the nearer end of the bottom edge or in place on the other edges. A `MutationObserver` follows the attribute through client-side navigation. A press on the mark, or turning the tools on from the off mark, opens the pill on that page without changing the stored choices. When a segment changes size, the other buttons glide to their new place instead of jumping. The pill and each open window have their own `view-transition-name`, so a page's View Transition leaves them in place, and they mount beside `<body>` so a router can replace it without disconnecting the tools or reloading their editors. It is the dark review toolbar of Drop on every page, with the system font, so the tools look the same on every site. The loader imports eager tools immediately; a `lazy: true` tool waits for activation, query selection, or restored tab state. It starts to load a lazy tool's script when the pointer reaches its button or the button gets focus, and inverts the button at once on a click. It calls the default export with `{ tool, bar, signal, open, exit, createWindow, createTab, onOpen, openTool, beforeExit }` (`ViteHubPageToolModule` and `ViteHubPageToolContext`):

- `bar` is the tool's segment: a `<vitehub-tool slot="<id>">` child of the pill. Attach a shadow root to it and draw the tool's controls there, so their CSS stays apart from the pill and from other tools. The pill's text color, font, dark `color-scheme`, and `--vitehub-pill-*` colors reach it. `--vitehub-pill-flow` is `row`, or `column` when the pill docks to the left or right edge: use it as the `flex-direction` of any row of controls inside the segment. Add `viteHubPillButtonStyles` from `@vite-hub/internal/runtime/page-tools-shared` to the segment's styles, so its buttons match the pill: 28 pixels high, and inverted while `aria-pressed` or `aria-expanded` is true. A segment that is still empty when the default export returns gets `hidden`. A tool can set `bar.hidden` later, for example to show its segment after a check.
- `createTab()` adds a tab to the pill: a `<vitehub-tab slot="tab">` child that stands on the bar's inner side, outside the bar's clip, like a tab on top of a chat box. It grows out from under the bar, unless the person asks for reduced motion, and it hides while the pill is collapsed. Draw it like `bar`, in its own shadow root with `viteHubPillButtonStyles`. Use it for a state of the page that the person must keep in view; the Content draft view is one. It goes away when the tool stops, or when the tool removes it.
- `open` is true for query selection or lazy activation and restoration. When a query selects an allowed tool, restored competitors mount with `open: false`.
- `exit()` first asks every `beforeExit` guard; if they all allow it, it removes the query, aborts every tool's `signal`, and replaces the pill with the ViteHub hexagon at 14px (20px on touch screens), half transparent, at the same place. `localStorage` keeps `vitehub-tools-off=1`, so the next pages draw only that mark: they still ask the session route, so the mark appears only while a tool allows the person, and `vitehub-tools` stays `1`. Pressing the mark, or opening a page with `?vitehub` or an allowed tool's link such as `?comment=3`, turns the tools on again; pressing it on the same page also restores the open windows. The pill's exit button calls `exit()`, so tools do not draw their own. Aborting also calls the cleanup function that the default export returned.

A failed startup aborts that attempt's `signal` and removes its retained windows and exit guards. A failed eager tool loses its segment; a failed lazy tool keeps a retry button and receives a fresh context on retry. The pill remains while a tool is mounted or available to launch or retry. The retained-window APIs are described below. The loader runs only in the browser, so `tsconfig.browser.json` checks it with the DOM library. The names and the session reader that the server and the loader share are in `@vite-hub/internal/runtime/page-tools-shared`. This API is internal: apps do not use it.

The Console and Comments are the page tools today. The Console registers `console`, a window that shows the Console in a same-origin frame, and `content`, the same window on the Content editor, for requests that its access policy accepts.

Owner packages expose inspection data through `vitehub.inspect` on their Vite plugin. The contributor returns `definitions` inspectors and `providerOutput` entries from `@vite-hub/internal/inspect`. `vitehub inspect` and the Console render that data. They do not own it.

Owner packages read Definitions that other Vite plugins add with `collectContributions` from `@vite-hub/internal/contributions`. A plugin sets `vitehub.<key>`, for example `vitehub.workspaces`, to an array or a factory of `{ name, definition: { module, export }, reason? }`. `module` is an absolute path, a `file:` URL, or a package specifier. `export` defaults to `default`. A factory receives `{ root, projectRoot, serverDirs }`, where `root` is always the Vite root. The collector returns the entries sorted by name with the contributing `plugin` name. It fails with the owner's diagnostic when two contributions use one name, and the message names both plugins. Owners add their own fields, such as the target `database`, and their own name rules.

Owner packages contribute Console sections with `ViteHubConsoleSectionContribution` from `@vite-hub/internal/console`. A contribution has an `id`, a `label`, an Iconify `icon`, a `description`, a `read` function that runs on the server, and a `view`. The view is a `definition-catalog` (Definitions in a sidebar with a detail panel) or a `record-table` (records in a table with a detail panel), and it has a `notice` that states which runtime data the section does not include. The Vue UI stays in `vite-hub`. For example, `@vite-hub/queue/vite` exports `queueConsoleSection`, and its `read` is `inspectQueueDefinitions`, so the Console and `vitehub inspect definitions` show the same Definitions. Record values are display strings. A record can also have a `link`, an app path or `https:` URL that the Console opens in a new tab, and an `activity` list, such as the comments of a thread, that the Console shows as a conversation. Do not put credentials in records. Set `filter: true` on a column with few values, such as a status, and the Console filters the table by its values with `?filter.<key>=<value>`. The Console also searches the id and every cell of the records with `?q=`.

A `record-table` section can also read records at request time. Add `runtime: { module, export }`, where `module` is an owner package path such as `@vite-hub/email/runtime/console` and `export` names a function that returns `ViteHubConsoleRecord[]` in the server runtime. `read` is then optional and returns the build-time records. The host imports the reader in its generated server code and calls it on each Console request, after the build-time records. A runtime record updates the build-time record with the same id: its cells and fields replace the build-time ones with the same key or label, and the others stay. `describeViteHubConsoleRuntimeReader` returns the checked reader, and `isViteHubConsoleRuntimeSection` tells the two record-table forms apart.

An `operation-view` section lists the result of one operation. It has `operation` (a registered name such as `comments.list`), `columns` (`key` is a dot path into each item, with `a|b` for a fallback, and `format` is `datetime` or `excerpt`), optional `filters` (chips, each with the `input` that it sends), an optional `link` built from a `template` such as `{subject.id}?comment={n}`, and an optional `detail`. With `detail: { kind: "comment-thread" }`, a row opens its item in a side panel as a comment thread, with replies, resolve, reopen, and mentions that call the `comments.*` operations; `?thread=<id>` opens it from the URL. The Console calls the operation over the RPC with the signed-in Console user, so the owner's policy decides per record what the user sees, and a failure shows its code and `fix`. It has no `read`. `@vite-hub/comments/vite` exports `commentsConsoleSection`; the Channels section can reuse the kind.

A `document-editor` section edits documents instead of showing records. It has `entry`, which returns the application module that holds the owner runtime (such as `server/content.ts`) or `undefined`, and `actions: { module, export }`, which names a `ViteHubConsoleDocumentActionsFactory`. The host shows the section only when `entry` finds a module, imports that module on the first request, and passes its namespace to the factory. The returned `ViteHubConsoleDocumentActions` (`collections`, `list`, `get`, `raw`, `save`, `remove`, `publish`, `revisions`, `restore`) receive the signed-in Console user, or `null`, and must check the owner policy themselves: the Console only checks the section. `publish` takes the draft digests the user reviewed and publishes nothing when one moved. Throw `createViteHubConsoleActionError({ status, code, message, details })` to return a code and details to the editor, such as per-field issues. Any other error becomes a `500` with a fixed message. `@vite-hub/content/vite` exports `contentConsoleSection`.

Runtime commands such as `vitehub agent dev` and `vitehub workspace dev` target a running Vite Development Server with `@vite-hub/internal/cli`: `readViteHubDevTargetOption` reads `--url`, `--server` and `--timeout`, `discoverViteHubDevServer` calls the discovery `GET`, and `fetchViteHubDevEndpoint` adds the guard header. The owner package registers the matching endpoint with `registerViteHubDevEndpoint` from `@vite-hub/internal/dev-endpoint`. It checks the `Host` header, the guard header, the request origin, and the JSON content type before the owner handler runs. The `Host` check uses Vite's host validation rules (`localhost`, IP literals, `server.host`, and `server.allowedHosts`). It blocks DNS rebinding, where a page on another host name resolves to the dev server and sends a matching `Origin`. An optional `authorize` callback runs owner authorization, for example a dev token check, after the guard checks. The handler receives a `ViteHubDevRequestGrant` for the request only after that check passes. A grant is frozen, bound to its request object, and valid only for that request. Only the checks in this module create grants. An operation that needs a checked request takes the grant and calls `assertViteHubDevRequestGrant(grant, request)`, which throws for a missing, forged, or other-request grant. Compare dev tokens and other request secrets with `isViteHubSecretEqual` from `@vite-hub/internal/secret`. Use `isViteHubBearerSecretEqual` for a `Bearer` `Authorization` header. Both compare in constant time and use no Node API, so they also run in Worker runtimes. Production routes use the same functions.

Some operations must run in the Nitro runtime, because the Nitro runtime owns the stores and registries. For these operations, `registerViteHubNitroDevEndpoint` registers the same guarded endpoint and forwards each `POST` with `forwardViteHubDevRequestToNitro`. The helper finds `server.environments.nitro` with `findViteHubNitroDevEnvironment`, calls the owner route under the Nitro `baseURL` (`viteHubNitroRuntimeRoute`), and adds the guard header. It requires the grant of the Vite guard check, because the forwarded request carries the guard header and the trusted `runtimeHeaders`. The discovery `GET` returns `runtime: "nitro"` or `runtime: "unavailable"`. When the Vite process has no Nitro environment, the `POST` returns `501` with a clear message. The owner package adds a `serve`-only Nitro handler whose source comes from `renderViteHubNitroDevHandler`. The owner module exports `defineEventHandler` for the generated handler. The handler passes the Nitro event to an owner runtime export. The export reads the Fetch `Request` with `toEventRequest` from `@vite-hub/internal/runtime/h3-v1-request`, because Nitro 2 (Nuxt 4) passes an H3 1 event whose `req` is Node's request. It then checks the request again with `validateViteHubNitroDevRequest`. That check returns `{ grant }` or `{ rejection }`. Its optional `authorize` callback runs owner authorization, for example a dev token check, before the grant exists. The export runs the operation only with the grant. The Nitro route is also reachable over HTTP on the dev server, and the Nitro runtime does not know `server.allowedHosts`. The Nitro check therefore accepts only the host names that the forwarder uses: `localhost`, `*.localhost`, and IP literals. It blocks DNS rebinding on the Nitro route.

Only Vite + Nitro hosts run Nitro in the Vite process. Nuxt runs Vite in middleware mode under its `buildAssetsDir` and runs Nitro in a separate dev worker, so the Vite middleware cannot dispatch into Nitro, and requests to the root dev endpoint do not reach the Vite middleware. Plain Vite has no Nitro. These hosts get the `501` response.

These helpers are dev-only. Dev endpoints trust the `Host` header, the guard header, the request origin, and a token file under the project root. A deployed stage has none of these, and no existing authenticated path reaches these endpoints on a deployed stage. Commands that target a deployed stage, such as `vitehub channels sync --stage <name> --url <origin>`, load the stage environment and call the provider APIs with its credentials.

`@vite-hub/internal/operations` defines `defineOperation()`, the operation registry, and the RPC client that the CLI uses. A Vite plugin contributes operations with `vitehub.operations: [{ module, export }]`. `vite-hub` installs them in the Console server plugin, and `@vite-hub/cli` makes a `vitehub <namespace> <command>` for each. Operations replace the per-package dev endpoints for new commands.

Operation section ids cannot contain `:`; it is reserved for scope and read-only grants. `defineOperation()` rejects a static section id with `:`, and a dynamic section that returns one denies the call. Use `scope` to require a grant such as `blob:media` for a call within a section.

Standalone KV, Blob, Email, and Rate Limit plugins install one local operation RPC before Nitro initializes. The generated handler runs their operations in the app's Nitro runtime. It is added only in serve mode and yields to the root integration's Console policy, including `console: false`. Local discovery checks the server's project identity; an explicit `--url` does not compare the deployed build's filesystem path with the CLI checkout.

Learn more at [vitehub.dev](https://vitehub.dev).

### Retained page-tool windows

A tool can set `lazy: true` to load its script on the first click. A failed import keeps a retry button. `?vitehub=<id>` opens that tool immediately. The loader remembers the last open window for the tab and app mount; it stores no document values.

The tool context provides `createWindow({ id, title, trigger, onHide?, colorScheme?, href? })`. `colorScheme` returns the `light` or `dark` scheme of what the window shows, so its title bar matches; without it, the window follows the system. `href` returns the full page URL of what the window shows. The title bar then has an **Open in new tab** link (`target="_blank"`, `rel="noopener"`) at every width, so a click, a middle-click, Cmd/Ctrl-click, and **Copy link** work. The window calls `href` again before the link is used, so it follows navigation inside the window. Without `href`, or while it returns `undefined`, the title bar has no link. Opening the tab leaves the window open. Its `body` holds the editor, and `show()` and `hide()` preserve that DOM. Expand, restore, resizing, and minimize all use the same mounted editor. Windows use the full available width on phones. Opening another tool minimizes the previous window. `signal` removes the window and its observers when tools stop.

`onOpen(handler)` handles activation from another tool. `openTool(id, path?)` starts an allowed tool on demand and sends it a relative path; it returns false when that tool is unavailable. The receiving owner validates and interprets the path. `beforeExit(check)` lets an owner protect pending work before the pill turns tools off. These APIs are internal.
