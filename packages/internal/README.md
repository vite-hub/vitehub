`@vite-hub/internal` is a private workspace package for shared implementation code. Application code should not import it.

## Install

Do not install this package directly. Other ViteHub packages depend on it inside the monorepo.

## Minimal API

```ts
// packages/*/src/internal-use.ts
import { createRuntimeRegistryContents } from "@vite-hub/internal/definition-catalog"
import { createNoExternalAddition } from "@vite-hub/internal/build/vite"
import { normalizeHosting } from "@vite-hub/internal/hosting"
import { summarizeDefinitions } from "@vite-hub/internal/inspect"
import { readViteHubConsoleSection } from "@vite-hub/internal/console"
import { discoverViteHubDevServer } from "@vite-hub/internal/cli"
import { registerViteHubDevEndpoint } from "@vite-hub/internal/dev-endpoint"
```

Source readers use `createSourceScanner(file)` from `@vite-hub/internal/source-scanner` to bind the file grammar. Its matching, splitting, object, and comment readers keep that grammar for source fragments. The standalone readers use JavaScript and TypeScript grammar without JSX. Filenames that end in `.jsx` or `.tsx` enable JSX, with TypeScript generic heads recognized only for `.tsx`.

## Used by

Packages use it for definition discovery, generated runtime registries, Provider Output, hosted runtime helpers, and hosting normalization.

The shared deployment output writer minifies identifiers, syntax, and whitespace in final Cloudflare, Vercel, and Netlify bundles. Each bundle can disable a pass with `bundleOptions.minifyIdentifiers: false`, `bundleOptions.minifySyntax: false`, or `bundleOptions.minifyWhitespace: false`. Netlify functions with an appended static config always minify identifiers to avoid config binding collisions. Syntax and identifier minification preserve function and class names, even when only one pass is enabled. Direct `bundleEsmEntry` calls leave all minification off by default, so intermediate generated sources are unchanged.

`readProvisionState` and `readProvisionStateSync` from `@vite-hub/internal/provision-state` return empty state when `.vitehub/provision.json` is missing. Invalid JSON and other read failures throw `INTERNAL_R0014` with the resolved path and original cause. `writeProvisionState` reads existing state before writing, so a read failure leaves the file unchanged. Valid JSON keeps its filtering policy: non-object roots become empty state, unsupported providers and invalid category shapes are skipped, and only string IDs are retained.

ViteHub writes its own Blob objects, such as Workspace history, Console attachments, and derived caches, under one prefix. `vitehubOwnedPrefix` from `@vite-hub/internal/owned-paths` is `_vitehub/`. Build every ViteHub-owned Blob path from it. `isVitehubOwnedPath(pathname)` returns true for those paths, so a UI that lists a Blob store can hide them and refuse to move or delete them.

Owner packages add a page tool, such as the Comments overlay, with `@vite-hub/internal/runtime/page-tools`. The owner's Nitro plugin calls `registerViteHubPageTool(nitroApp, { id, label, icon, hotkey?, script, allowed })` and then `installViteHubPageTools(nitroApp)`. One hint decides whether a page gets anything: the `?vitehub` query (`?vitehub=<id>` also opens that tool) or the `vitehub-tools=1` cookie. With the hint and at least one registered tool, the install adds one loader tag, `<script type="module" src="/_vitehub/page/assets/loader.js?v=2" data-vitehub-page-tools>`, before `</body>`, with the page's CSP nonce, and sends that page with `cache-control: private, no-store`. It installs once per Nitro app: on Nitro 3 it wraps `fetch`, and on Nitro 2 it hooks `render:html` and `beforeResponse`. Paths under `/_vitehub` and `/api/` never get the loader. Owners with a mounted application base pass its pathname to `installViteHubPageTools(nitroApp, base)`, which excludes those routes under that base too. The base is kept per app and can be supplied after another owner installed the hooks. Tools belong to one Nitro app. A second register with the same `id` replaces only that app's tool. Registrations before or after installation are visible on the next request, including registrations from separately bundled owner packages.

`GET /_vitehub/page/session` runs `allowed({ request, event })` of each tool registered for the requesting Nitro app and returns `{ tools: [{ id, label, icon, hotkey?, script }] }` with `cache-control: private, no-store`. It sets the hint cookie when at least one tool is allowed and clears it when none is. A check that throws counts as not allowed. A request with another `Origin`, or with `Sec-Fetch-Site: cross-site`, gets 403 and runs no check. The hint is never a credential: each tool's API checks access on every call. The owner's Vite plugin serves the route and the loader with `addViteHubPageToolRoutes(kit, { handler, loader, base })` from `@vite-hub/internal/build/page-tools`, so they work without the Console. Use the same application `base` for route registration and `installViteHubPageTools(nitroApp, base)`; for `/portal`, both the loader and session live under `/portal/_vitehub/page`. The browser entry passes `new URL("../session", import.meta.url).pathname` as the loader's `session` option. The first owner wins; the registry is shared through a `globalThis` slot, so any copy of the handler answers for that app's tools. The Nitro 3 fetch wrapper binds each request to its app; the Nitro 2 request hook binds each H3 event. Without a binding the handler returns 503 and runs no permission checks.

The loader, `loadViteHubPageTools()` from `@vite-hub/internal/runtime/page-tools-loader`, calls the session route. Without an allowed tool it stops. Otherwise it draws the pill: one `<vitehub-pill>` element with an open shadow root, fixed at the bottom center of the page. The pill has one named slot per tool, in session order, and one exit button, **Turn off ViteHub tools**. It follows the page's light or dark scheme (a `dark` or `light` class, `data-theme`, or `color-scheme` on `<html>`) through `color-scheme`, and takes the page's font. The loader then imports each `script` and calls its default export with `{ tool, bar, signal, open, exit }` (`ViteHubPageToolModule` and `ViteHubPageToolContext`):

- `bar` is the tool's segment: a `<vitehub-tool slot="<id>">` child of the pill. Attach a shadow root to it and draw the tool's controls there, so their CSS stays apart from the pill and from other tools. The pill's text color, font, and `color-scheme` reach it, so `light-dark()` works. A segment that is still empty when the default export returns gets `hidden`. A tool can set `bar.hidden` later, for example to show its segment after a check.
- `open` is true when `?vitehub=<id>` names the tool.
- `exit()` clears the cookie and the query, aborts every tool's `signal`, and removes the pill. The pill's exit button calls it, so tools do not draw their own. The loader then calls the cleanup function that the default export returned.

A tool whose script fails loses its segment. When no tool starts, the loader removes the pill. The loader runs only in the browser, so `tsconfig.browser.json` checks it with the DOM library. The names and the session reader that the server and the loader share are in `@vite-hub/internal/runtime/page-tools-shared`. This API is internal: apps do not use it.

The Console and Comments are the page tools today. The Console registers `console`, a link that opens the Console in a new tab, for requests that its access policy accepts.

Owner packages expose inspection data through `vitehub.inspect` on their Vite plugin. The contributor returns `definitions` inspectors and `providerOutput` entries from `@vite-hub/internal/inspect`. `vitehub inspect` and the Console render that data. They do not own it.

Owner packages read Definitions that other Vite plugins add with `collectContributions` from `@vite-hub/internal/contributions`. A plugin sets `vitehub.<key>`, for example `vitehub.workspaces`, to an array or a factory of `{ name, definition: { module, export }, reason? }`. `module` is an absolute path, a `file:` URL, or a package specifier. `export` defaults to `default`. A factory receives `{ root, projectRoot, serverDirs }`, where `root` is always the Vite root. The collector returns the entries sorted by name with the contributing `plugin` name. It fails with the owner's diagnostic when two contributions use one name, and the message names both plugins. Owners add their own fields, such as the target `database`, and their own name rules.

Owner packages contribute Console sections with `ViteHubConsoleSectionContribution` from `@vite-hub/internal/console`. A contribution has an `id`, a `label`, an Iconify `icon`, a `description`, a `read` function that runs on the server, and a `view`. The view is a `definition-catalog` (Definitions in a sidebar with a detail panel) or a `record-table` (records in a table with a detail panel), and it has a `notice` that states which runtime data the section does not include. The Vue UI stays in `vite-hub`. For example, `@vite-hub/queue/vite` exports `queueConsoleSection`, and its `read` is `inspectQueueDefinitions`, so the Console and `vitehub inspect definitions` show the same Definitions. Record values are display strings. A record can also have a `link`, an app path or `https:` URL that the Console opens in a new tab, and an `activity` list, such as the comments of a thread, that the Console shows as a conversation. Do not put credentials in records.

A `record-table` section can also read records at request time. Add `runtime: { module, export }`, where `module` is an owner package path such as `@vite-hub/email/runtime/console` and `export` names a function that returns `ViteHubConsoleRecord[]` in the server runtime. `read` is then optional and returns the build-time records. The host imports the reader in its generated server code and calls it on each Console request, after the build-time records. A runtime record replaces a build-time record with the same id. `describeViteHubConsoleRuntimeReader` returns the checked reader, and `isViteHubConsoleRuntimeSection` tells the two record-table forms apart.

An `operation-view` section lists the result of one operation. It has `operation` (a registered name such as `comments.list`), `columns` (`key` is a dot path into each item, with `a|b` for a fallback, and `format` is `datetime` or `excerpt`), optional `filters` (chips, each with the `input` that it sends), and an optional `link` built from a `template` such as `{subject.id}?comment={n}`. The Console calls the operation over the RPC with the signed-in Console user, so the owner's policy decides per record what the user sees, and a failure shows its code and `fix`. It has no `read`. `@vite-hub/comments/vite` exports `commentsConsoleSection`; the Channels section can reuse the kind.

A `document-editor` section edits documents instead of showing records. It has `entry`, which returns the application module that holds the owner runtime (such as `server/content.ts`) or `undefined`, and `actions: { module, export }`, which names a `ViteHubConsoleDocumentActionsFactory`. The host shows the section only when `entry` finds a module, imports that module on the first request, and passes its namespace to the factory. The returned `ViteHubConsoleDocumentActions` (`collections`, `list`, `get`, `raw`, `save`, `remove`, `publish`, `revisions`, `restore`) receive the signed-in Console user, or `null`, and must check the owner policy themselves: the Console only checks the section. `publish` takes the draft digests the user reviewed and publishes nothing when one moved. Throw `createViteHubConsoleActionError({ status, code, message, details })` to return a code and details to the editor, such as per-field issues. Any other error becomes a `500` with a fixed message. `@vite-hub/content/vite` exports `contentConsoleSection`.

Runtime commands such as `vitehub agent dev` and `vitehub workspace dev` target a running Vite Development Server with `@vite-hub/internal/cli`: `readViteHubDevTargetOption` reads `--url`, `--server` and `--timeout`, `discoverViteHubDevServer` calls the discovery `GET`, and `fetchViteHubDevEndpoint` adds the guard header. The owner package registers the matching endpoint with `registerViteHubDevEndpoint` from `@vite-hub/internal/dev-endpoint`. It checks the `Host` header, the guard header, the request origin, and the JSON content type before the owner handler runs. The `Host` check uses Vite's host validation rules (`localhost`, IP literals, `server.host`, and `server.allowedHosts`). It blocks DNS rebinding, where a page on another host name resolves to the dev server and sends a matching `Origin`. An optional `authorize` callback runs owner authorization, for example a dev token check, after the guard checks. The handler receives a `ViteHubDevRequestGrant` for the request only after that check passes. A grant is frozen, bound to its request object, and valid only for that request. Only the checks in this module create grants. An operation that needs a checked request takes the grant and calls `assertViteHubDevRequestGrant(grant, request)`, which throws for a missing, forged, or other-request grant. Compare dev tokens and other request secrets with `isViteHubSecretEqual` from `@vite-hub/internal/secret`. Use `isViteHubBearerSecretEqual` for a `Bearer` `Authorization` header. Both compare in constant time and use no Node API, so they also run in Worker runtimes. Production routes use the same functions.

Some operations must run in the Nitro runtime, because the Nitro runtime owns the stores and registries. For these operations, `registerViteHubNitroDevEndpoint` registers the same guarded endpoint and forwards each `POST` with `forwardViteHubDevRequestToNitro`. The helper finds `server.environments.nitro` with `findViteHubNitroDevEnvironment`, calls the owner route under the Nitro `baseURL` (`viteHubNitroRuntimeRoute`), and adds the guard header. It requires the grant of the Vite guard check, because the forwarded request carries the guard header and the trusted `runtimeHeaders`. The discovery `GET` returns `runtime: "nitro"` or `runtime: "unavailable"`. When the Vite process has no Nitro environment, the `POST` returns `501` with a clear message. The owner package adds a `serve`-only Nitro handler whose source comes from `renderViteHubNitroDevHandler`. The handler calls an owner runtime export, and that export checks the request again with `validateViteHubNitroDevRequest`. That check returns `{ grant }` or `{ rejection }`. Its optional `authorize` callback runs owner authorization, for example a dev token check, before the grant exists. The export runs the operation only with the grant. The Nitro route is also reachable over HTTP on the dev server, and the Nitro runtime does not know `server.allowedHosts`. The Nitro check therefore accepts only the host names that the forwarder uses: `localhost`, `*.localhost`, and IP literals. It blocks DNS rebinding on the Nitro route.

Only Vite + Nitro hosts run Nitro in the Vite process. Nuxt runs Vite in middleware mode under its `buildAssetsDir` and runs Nitro in a separate dev worker, so the Vite middleware cannot dispatch into Nitro, and requests to the root dev endpoint do not reach the Vite middleware. Plain Vite has no Nitro. These hosts get the `501` response.

These helpers are dev-only. Dev endpoints trust the `Host` header, the guard header, the request origin, and a token file under the project root. A deployed stage has none of these, and no existing authenticated path reaches these endpoints on a deployed stage. Commands that target a deployed stage, such as `vitehub channels sync --stage <name> --url <origin>`, load the stage environment and call the provider APIs with its credentials.

`@vite-hub/internal/operations` defines `defineOperation()`, the operation registry, and the RPC client that the CLI uses. A Vite plugin contributes operations with `vitehub.operations: [{ module, export }]`. `vite-hub` installs them in the Console server plugin, and `@vite-hub/cli` makes a `vitehub <namespace> <command>` for each. Operations replace the per-package dev endpoints for new commands.

Standalone KV, Blob, Email, and Rate Limit plugins install one local operation RPC before Nitro initializes. The generated handler runs their operations in the app's Nitro runtime. It is added only in serve mode and yields to the root integration's Console policy, including `console: false`. Local discovery checks the server's project identity; an explicit `--url` does not compare the deployed build's filesystem path with the CLI checkout.
