# Access-Owned Workspace Source Grants

## Decision

Workspace Sources should carry a stable Source key and the mechanics needed to retrieve and place content. They should not declare Workspace Scope membership or imply authorization. `access()` should own every Source grant, while Invocation-Scoped Source Resolution should continue to turn a universal Source into a concrete repository, root, Mount, and fingerprint for one already-authorized Agent Invocation.

The intended public shape is:

```ts
const workspace = defineWorkspace({
  sources: {
    ingestion: github(({ channel }) => {
      const customer = channel?.meta?.customer
      const suffix = customer ? `/${customer}` : ''

      return {
        repo: 'quiverdk/ingestion',
        root: `dbt${suffix}`,
        mount: `ingestion${suffix}`,
      }
    }),
  },
})

const agent = defineAgent({
  workspace,
  capabilities: [
    access({
      workspace: {
        resolve({ run }) {
          return run?.channelId === 'support' ? 'support' : 'technical'
        },
        scopes: {
          support: { sources: ['ingestion'] },
          technical: { sources: ['ingestion'] },
        },
      },
    }),
    workspaceShell({ mode: 'read' }),
  ],
})
```

`ingestion` is universal because its identity and resolver are independent of an audience. It is not implicitly public: both Workspace Scopes receive an explicit grant from `access()`. The trusted Channel customer context only chooses `dbt` versus `dbt/<customer>` and `ingestion` versus `ingestion/<customer>` after Access has selected the invocation's Workspace Scope.

## ViteHub evidence

The original capability contract already put typed Source grants in Access. PR [#233](https://github.com/vite-hub/vitehub/pull/233) added `source`, `sources`, and `grants` to Access Workspace Scope definitions and carried the referenced Source names through `AccessCapabilityTypeContract.workspaceSources`; `defineAgent()` then checked those names against the Workspace Source Map. The corresponding ADR says Capability Type Contracts may reject mismatched Source keys, while runtime authority remains in explicit Capability resolvers rather than inferred TypeScript types. ([Access types at merge commit](https://github.com/vite-hub/vitehub/blob/858384baa1de41e168b02ba88f09c6e630e28e96/packages/agent/src/capabilities/access.ts#L103-L215); [ADR 0038 at the same commit](https://github.com/vite-hub/vitehub/blob/858384baa1de41e168b02ba88f09c6e630e28e96/.agents/adr/0038-capability-type-contracts.md#L1-L14))

PR [#272](https://github.com/vite-hub/vitehub/pull/272) introduced Invocation-Scoped Source Resolution with the opposite ownership boundary from source-owned scopes: Access remains the authorization boundary, while resolution shapes a Source's concrete origin and Mount from trusted invocation context and the Selected Workspace Scope. Its ADR explicitly rejected letting Sources read arbitrary invoker metadata as authorization logic and rejected letting `access()` mutate Workspace Definitions. ([ADR 0042 at merge commit](https://github.com/vite-hub/vitehub/blob/406031a8157abc47db9cd65d698091a9d066ac16/.agents/adr/0042-invocation-scoped-source-resolution.md#L1-L16); [initial resolver implementation](https://github.com/vite-hub/vitehub/blob/406031a8157abc47db9cd65d698091a9d066ac16/packages/workspace/src/sources/resolution.ts#L21-L50))

PR [#371](https://github.com/vite-hub/vitehub/pull/371) made that ordering enforceable by applying the Selected Workspace Scope before Source-backed overlays are read. ([scoped Source facade at merge commit](https://github.com/vite-hub/vitehub/blob/14212e56e912ce3f7f1b24506d4d0e0953b785df/packages/workspace/src/sources/resolution.ts#L263-L310)) PR [#497](https://github.com/vite-hub/vitehub/pull/497) preserved the same restriction for writable harness Workspace Sessions. ([scoped session handling at merge commit](https://github.com/vite-hub/vitehub/blob/dedb2441444d9420beca345abf41bb48fc6a2bd3/packages/agent/src/capabilities/access.ts#L760-L865)) These changes matter because removing Source scope membership must not remove path enforcement; Access still produces the scoped facade that all later Capabilities and sessions receive.

PR [#417](https://github.com/vite-hub/vitehub/pull/417) added `WorkspaceSource.scopes` to avoid repeating Source keys across Access scopes, then derived additive Access grants from that metadata. Its ADR records convenience as the reason: explicit `access.workspace.scopes[scope].sources` entries were considered duplicate authoring. ([ADR 0074 at merge commit](https://github.com/vite-hub/vitehub/blob/40ab01e8c36a2a5230d63855371435ae1881ed22/.agents/adr/0074-source-scoped-access-derives-source-grants.md#L1-L9)) That trade-off does not hold for a universal dynamic Source. A Source shared by support and technical access has no single audience of its own, so placing both names on the Source makes the resource describe its consumers and still duplicates policy. Customer-specific or tenant-specific scopes make the mismatch worse because Source identity is stable while authorization selections are invocation-dependent.

PR [#541](https://github.com/vite-hub/vitehub/pull/541) exposed canonical `channel` context to Source resolvers and allowed named Source scopes without duplicate empty Access scope entries. The useful half is the trusted-context path, which is independent of Source-owned authorization: current Agent types register `channel` in both Agent Invocation Context Values and Workspace Source Resolution Context, and the Chat trigger builds it from the server-owned trigger input. ([registered context at `ff8e0b4`](https://github.com/vite-hub/vitehub/blob/ff8e0b4e4d24f58a622e190c426c4d24eaf7d177/packages/agent/src/chat-trigger.ts#L94-L108); [trigger input construction](https://github.com/vite-hub/vitehub/blob/ff8e0b4e4d24f58a622e190c426c4d24eaf7d177/packages/agent/src/chat-message-input.ts#L298-L347)) Authentication and trusted-field admission must happen before those values enter the Agent Invocation; model messages remain untrusted data. ([Channel trust guidance at the research base](https://github.com/vite-hub/vitehub/blob/e478b1b04385b54a31b4ed48c01d9fd30ec7899d/docs/content/docs/agents/channels.md#L127-L147))

At the research base commit `e478b1b04385b54a31b4ed48c01d9fd30ec7899d`, Access already performs the correct lifecycle: it resolves a Workspace Scope, passes the Selected Workspace Scope plus filtered invocation context into Source Resolution, recalculates grants against the resolved definition, and only then replaces the active Workspace with a scoped facade. ([Access lifecycle](https://github.com/vite-hub/vitehub/blob/e478b1b04385b54a31b4ed48c01d9fd30ec7899d/packages/agent/src/capabilities/access.ts#L284-L363); [Source resolver context and result application](https://github.com/vite-hub/vitehub/blob/e478b1b04385b54a31b4ed48c01d9fd30ec7899d/packages/workspace/src/sources/resolution.ts#L520-L603)) The implementation to remove is the intermediate derivation from `WorkspaceSource.scopes`, not the lifecycle around it. ([Source-owned derivation](https://github.com/vite-hub/vitehub/blob/e478b1b04385b54a31b4ed48c01d9fd30ec7899d/packages/agent/src/capabilities/access.ts#L379-L437))

Workspace Sources can also enter an Agent through Capabilities. Static `capability.workspaceSources` are normalized and merged into the Workspace Definition during Agent construction, while invocation-time `capability.workspace` contributions are merged after earlier Capability phases have established trusted context. ([static Capability Source collection](https://github.com/vite-hub/vitehub/blob/e478b1b04385b54a31b4ed48c01d9fd30ec7899d/packages/agent/src/capability-runtime.ts#L259-L273); [Agent Workspace merge](https://github.com/vite-hub/vitehub/blob/e478b1b04385b54a31b4ed48c01d9fd30ec7899d/packages/agent/src/workspace-agent.ts#L213-L235); [invocation-time contribution lifecycle](https://github.com/vite-hub/vitehub/blob/e478b1b04385b54a31b4ed48c01d9fd30ec7899d/packages/agent/src/capability-runtime.ts#L665-L740)) Access-owned Source keys therefore have to survive as trusted selection state until both contribution paths have produced the final Workspace Definition; reducing authorization to an early list of Mount paths would incorrectly reject or hide a granted Source whose concrete Mount does not exist until a Capability contributes or resolves it.

The current public docs already state the desired semantic rule: Source Resolution is source shaping, not authorization, and Access decides which paths are visible. ([Workspace Context docs](https://github.com/vite-hub/vitehub/blob/e478b1b04385b54a31b4ed48c01d9fd30ec7899d/docs/content/docs/agents/workspace-context.md#L144-L197)) The implementation should make that documented distinction true everywhere instead of retaining a second grant authoring surface on Source Bindings.

PR [#580](https://github.com/vite-hub/vitehub/pull/580) is adjacent but does not own this seam. It attaches static Capability lists to Channels and changes Channel/Agent Capability composition; its current file set does not change `access.ts`, Workspace Source types, Source Resolution, or Workspace docs. Channel attachment can decide which capabilities exist for a Channel, but the attached `access()` Capability must still own per-invocation Workspace authorization.

## Primary-source analogues

Better Auth keeps resource/action vocabulary and role grants inside its access-control subsystem. `createAccessControl()` creates roles from statements, and each role's `authorize()` checks requested resources and actions against that role's statements; the protected resource implementation does not declare which roles may use it. Its organization plugin follows the same pattern by defining `organization`, `member`, `invitation`, `team`, and `ac` resources once, then assigning different action sets to owner, admin, and member roles. ([Better Auth access implementation](https://github.com/better-auth/better-auth/blob/54fab084469a27257e66a0814523ebac7145ef5d/packages/better-auth/src/plugins/access/access.ts#L106-L168); [organization role statements](https://github.com/better-auth/better-auth/blob/54fab084469a27257e66a0814523ebac7145ef5d/packages/better-auth/src/plugins/organization/access/statement.ts#L3-L41); [official Admin access-control docs](https://www.better-auth.com/docs/plugins/admin#access-control)) The ViteHub analogue is a Source key declared once and referenced by one or more Access Workspace Scope grants.

OAuth Resource Indicators separates the target resource from authorization scope. RFC 8707 says scope usually expresses what access is requested, while the `resource` parameter identifies where the token will be used; the authorization server combines them and applies policy, including tenant-specific audience restrictions. ([RFC 8707, introduction and resource parameter](https://www.rfc-editor.org/rfc/rfc8707.html#section-2); [security considerations](https://www.rfc-editor.org/rfc/rfc8707.html#section-3)) A resolved repository/root/Mount is ViteHub's concrete target identity, while Access grants express whether the invocation may see it.

Cedar models an authorization request as principal, action, resource, and context, then evaluates that request against a separate policy store with default deny. Resource entity data and request context inform the decision, but they are not the policies themselves. ([Cedar authorization model](https://docs.cedarpolicy.com/auth/authorization.html); [Cedar entities and context](https://docs.cedarpolicy.com/auth/entities-syntax.html)) ViteHub should likewise pass the resolved Source and trusted customer context through the access lifecycle without embedding the grant policy in the Source.

GitHub Apps also keep permissions and repository access as explicit installation/token authority. An installation grants requested permissions and separately selects all or specific repositories, while an installation token may narrow both repositories and permissions but cannot broaden beyond the installation. ([GitHub App permissions](https://docs.github.com/en/apps/creating-github-apps/registering-a-github-app/choosing-permissions-for-a-github-app); [installation access tokens](https://docs.github.com/en/enterprise-cloud@latest/apps/creating-github-apps/authenticating-with-a-github-app/generating-an-installation-access-token-for-a-github-app)) A GitHub repository does not carry the app roles that may access it, so a ViteHub `github()` Source should not carry Agent Workspace Scope membership either.

## Required API and plumbing changes

1. Remove `scopes` from `WorkspaceSource`, Workspace Source Binding options, every Source helper's runtime-option picks, normalization, fingerprints, metadata mirrors, generated types, and public docs. `defineAgent()` validation should reject source-local `scopes` on both raw Source objects and `{ source, ...binding }` wrappers, whether the Source is declared directly in the Workspace or supplied through static `capability.workspaceSources`; it must not become ignored compatibility data after structural inference. The current surface is centralized in `WorkspaceSource` and `WorkspaceSourceBindingOptions`, then copied through every helper. ([Workspace Source types at the research base](https://github.com/vite-hub/vitehub/blob/e478b1b04385b54a31b4ed48c01d9fd30ec7899d/packages/workspace/src/core/types.ts#L430-L505); [normalization](https://github.com/vite-hub/vitehub/blob/e478b1b04385b54a31b4ed48c01d9fd30ec7899d/packages/workspace/src/sources/config.ts#L105-L176); [Capability Source surface](https://github.com/vite-hub/vitehub/blob/e478b1b04385b54a31b4ed48c01d9fd30ec7899d/packages/agent/src/types.ts#L792-L821))
2. Keep `WorkspaceSourceResolver`, `selectedWorkspaceScope`, and filtered Agent Invocation Context Values. Resolution may return a concrete Source or `false`; returning `false` means the Source cannot be concretized for this invocation, not that the resolver is an authorization policy. ([resolution context types](https://github.com/vite-hub/vitehub/blob/e478b1b04385b54a31b4ed48c01d9fd30ec7899d/packages/workspace/src/core/types.ts#L312-L355))
3. Keep Source grants only in `AccessWorkspaceScopeDefinition` and inline `access.workspace.resolve()` selections. Remove `withWorkspaceSourceScopeGrants()` and the runtime/type validators whose only job is reconciling Source-local scope names with Access scope names. ([Access grant surface](https://github.com/vite-hub/vitehub/blob/e478b1b04385b54a31b4ed48c01d9fd30ec7899d/packages/agent/src/capabilities/access.ts#L128-L203); [grant-to-path resolution](https://github.com/vite-hub/vitehub/blob/e478b1b04385b54a31b4ed48c01d9fd30ec7899d/packages/agent/src/capabilities/access.ts#L519-L608))
4. Preserve `AccessCapabilityTypeContract.workspaceSources` and `defineAgent()`'s `ValidateCapabilityWorkspaceSources`. Literal Source-name validation must compare Access grants against the union of Workspace Source keys and recursively normalized static `capability.workspaceSources` keys, so `access()` can grant a Source contributed by another Capability while still rejecting a typo. Remove `workspaceScopes` from the type contract only if no other contract consumes it after the Source-scope validator is deleted. ([type-contract validator at the research base](https://github.com/vite-hub/vitehub/blob/e478b1b04385b54a31b4ed48c01d9fd30ec7899d/packages/agent/src/index.ts#L417-L474); [static Capability Source collection](https://github.com/vite-hub/vitehub/blob/e478b1b04385b54a31b4ed48c01d9fd30ec7899d/packages/agent/src/capability-runtime.ts#L259-L273))
5. Keep Access first in Capability order, but carry its explicit Source keys as part of the trusted Selected Workspace Scope instead of collapsing them immediately to paths. Capability contribution filtering should accept a Source by a trusted granted key, pass those keys with the Selected Workspace Scope into dynamic Source Resolution, then recalculate final path and materialization grants against the expanded, resolved Workspace Definition before constructing the scoped facade. The recalculated paths must be written back with the trusted Access context so later Capability contributions and sessions see the same authorization decision. ([ordering check](https://github.com/vite-hub/vitehub/blob/e478b1b04385b54a31b4ed48c01d9fd30ec7899d/packages/agent/src/capability-runtime.ts#L226-L280); [contribution filtering and final Source facade](https://github.com/vite-hub/vitehub/blob/e478b1b04385b54a31b4ed48c01d9fd30ec7899d/packages/agent/src/capability-runtime.ts#L665-L740))
6. `defineCapability()` does not need a new runtime mutation hook for this boundary. Its existing static `workspaceSources` field, invocation-time `workspace` contribution resolver, ordered phases, and type contract are sufficient if the contribution lifecycle carries trusted Access Source keys through filtering and final path recalculation. ([Capability definition and validator](https://github.com/vite-hub/vitehub/blob/e478b1b04385b54a31b4ed48c01d9fd30ec7899d/packages/agent/src/types.ts#L792-L821); [`defineCapability()` validation](https://github.com/vite-hub/vitehub/blob/e478b1b04385b54a31b4ed48c01d9fd30ec7899d/packages/agent/src/capability-runtime.ts#L197-L218))

## Regression boundary

The regression should declare one dynamic `ingestion` GitHub Source with no audience field. Both `support` and `technical` Access Workspace Scopes should explicitly grant `sources: ['ingestion']`. Two invocations should supply different authenticated Channel customer values and prove that each reads only the corresponding resolved Mount, with the resolver observing both the selected Workspace Scope and canonical `channel` context.

The proof should also assert that the resolved GitHub options are `quiverdk/ingestion` plus `dbt/<customer>` and `ingestion/<customer>`, that a typo in an Access Source grant still fails the existing Type Contract, and that raw and wrapped `scopes` are no longer accepted on direct or static Capability-contributed Workspace Sources. A focused Capability-contribution case should grant a static contributed Source by key before it has a final Mount, then prove contribution filtering, dynamic resolution, final path recalculation, and scoped reads all preserve that grant. This covers the authorization owner, both Source contribution paths, dynamic shaping, trusted context, and the breaking public API in one narrow story.

## Rejected alternatives and objections

- Keeping Source `scopes` as optional labels preserves colocated authoring, but it makes a stable resource definition enumerate every access policy that consumes it. A universal Source then repeats policy names at the wrong layer, while dynamic tenant scopes can make that list unbounded.
- Treating a resolver's `false` return as authorization would hide policy in retrieval code and make grants harder to inspect. It should only mean that trusted context cannot produce a concrete Source after Access has already granted the Source key.
- Moving grants to Channel Definitions would confuse reachability with authorization. PR #580 can attach an `access()` Capability to a Channel, but the Capability must remain the inspectable owner of Workspace grants.
- Adding an Access builder or shared grant DSL solely to avoid writing `sources: ['ingestion']` twice is premature. The repetition is meaningful because support and technical are separate policy statements; a helper can be added later if repeated policy composition proves common.
